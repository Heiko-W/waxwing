# ADR-023 — A Sieve script we did not write is preserved verbatim, never parsed

- **Status:** accepted
- **Date:** 2026-08-19
- **Work package:** M5.2 (Filter rules) — implements FR-SIEVE-01, FR-SIEVE-02
- **Method:** RFC 9661 read in full; Stalwart behaviour read from `main` @ `9497a5d` (2026-08-18);
  four other JMAP clients' filter implementations read as prior art

## Context

FR-SIEVE-01 asks for a visual rule builder on top of JMAP for Sieve, and states the hard part in
one clause: *"round-trip-safe (foreign scripts are shown read-only in a code view rather than
destroyed)"*.

The difficulty is that Sieve is a real language and a rule builder is not. A builder can express a
handful of conditions and actions; a script can contain anything. The mailbox this ships into may
already have a script — hand-written, or generated by Roundcube, Nextcloud, Horde or an
administrator — and only one script per account can be active (RFC 9661 §2.1). So the builder
cannot simply write its own file and ignore the rest: whatever it activates is what filters the
user's mail, and everything else stops running.

Every client of this shape solves it by parsing the existing script back into rules. That is where
they break. The most developed open implementation (Bulwark, ~1150 lines across a generator and a
parser) carries an `isOpaque` bail-out, a dedicated external-rules preservation block and a
special case for Nextcloud's marker comments — all of it added after
[an issue](https://github.com/bulwarkmail/webmail/issues/201) in which editing a rule deleted the
user's Nextcloud filters. Its parser still degrades any Roundcube rule using `setflag` to opaque,
because the parser does not know that command.

The failure mode is worth naming precisely: **a rule editor that half-understands a script will
rewrite it into what it did understand.** The user sees a rule list that looks right, and mail
starts going somewhere else.

## Decision

Do not parse Sieve. Three rules:

1. **Our rules are stored as JSON in a marker comment, and read back from there — never by
   re-parsing the Sieve we generated.** `# @waxwing:rules:v1 {…}` opens the managed region,
   `# @waxwing:rules:end` closes it. Generation is one-way: model → Sieve. The vocabulary the
   builder can express is therefore exactly the vocabulary it can read, by construction rather
   than by keeping two parsers in agreement.

2. **Everything outside the markers is foreign, and is carried across a save byte for byte, in its
   original position.** Position, not just bytes: Sieve is evaluated in order and a foreign `stop;`
   or `fileinto` decides whether later rules run at all, so moving someone's rules below ours would
   change what their mail does while claiming to have preserved them. The only thing that moves is
   their `require` line, which is merged with ours — RFC 5228 §3.2 requires every `require` to
   precede the first command, so two `require` lines in sequence would not compile.

3. **Any doubt makes the whole script opaque.** Malformed JSON, a schema version we do not know, a
   rule shape that fails validation, a second opening marker: the section shows the script
   read-only and offers no rule editing at all. A newer version's script is deliberately included
   here — it may use conditions this build cannot render, and saving would silently drop them.

A foreign script is therefore never edited *in place*. The section shows it and offers one action:
manage filters **alongside** it. That keeps their script running, adds our region after it, and is
phrased that way in the UI because the alternative the user would otherwise assume — that we
understood their script well enough to edit it — is the promise this design refuses to make.

## Consequences

**What this costs.** A user who already has filters cannot edit them here. They see them, and they
can add ours next to them, but the existing rules stay where they are. That is a real limitation
and it is the intended one: the alternative is an editor that sometimes rewrites rules it
misread.

**What it avoids.** There is no Sieve parser in the bundle, no per-generator special cases, and no
class of bug where a rule silently changes meaning after a round trip. The `# @waxwing:rules:v1`
marker is a `#` line comment rather than a `/* … */` block precisely so that no user-supplied text
can close it early — `JSON.stringify` escapes CR and LF inside strings, so a rule named with a
newline cannot terminate the comment, which is the same class of bug as an unescaped `*/` inside a
block comment (a defect Bulwark's block-comment metadata is exposed to).

**Marker stability.** The version in the marker is a promise: a future build that widens the rule
vocabulary bumps it, and an older build then treats the script as opaque rather than dropping what
it cannot represent.

## Protocol notes that shaped the client

Recorded here because each one produces a plausible-looking client that misbehaves, and none is
obvious from the RFC alone:

- **Script content is never inline.** It is uploaded as a blob and referenced by id (RFC 9661
  §2.2). Drafts -01 and -02 did carry a `content` string, which is why examples of it are still
  easy to find; -03 reverted it and no shipping server accepts it. The blob id a `/set` returns is
  *not* the uploaded one.
- **`onSuccessActivateScript: null` does not deactivate.** The RFC requires an absent, invalid or
  unknown id to be ignored, leaving the active script active — so a client that sends `null` to
  turn filtering off leaves the old script filtering mail while its UI says filtering is off.
  Deactivation is `onSuccessDeactivateScript: true`.
- **Stalwart still emits the pre-RFC error spellings.** Draft -17 renamed `invalidScript` →
  `invalidSieve` and `scriptIsActive` → `sieveIsActive`; Stalwart sends the old pair. Matching only
  the RFC spelling turns "your script does not compile" into an unrecognised failure, so both are
  matched (`isInvalidSieveError`, `isSieveIsActiveError`).
- **A `/set` echo cannot be trusted to report activation.** RFC 9661 §2.4 requires an activated
  script to appear in `created`/`updated` and a deactivated one in `updated`; Stalwart returns an
  empty `updated` for an activation-only call. Every mutation re-reads.
- **`SieveScript/validate` does not check `require`.** Stalwart compiles a script containing a
  `require` for an extension it does not implement and only fails at delivery time, so a clean
  validate is not proof the script will run. The section checks the extensions it needs against
  the account capability's `sieveExtensions` itself and warns.
- **The active script cannot be destroyed in the same call that deactivates it** (RFC 9661 §2.4) —
  `destroy` therefore issues two.
- **`fileinto` addresses the mailbox by id first, name second** (`fileinto :mailboxid "<id>"
  "<name>"`, RFC 9042 §4): the id survives a rename, the name keeps the script readable and gives
  the server something to fall back on.

## Alternatives considered

**Parse foreign Sieve into read-only rule rows** (Bulwark's approach). Rejected: it is the largest
piece of code in the feature, it is the part every implementation has had bugs in, and it buys
display only — the rows still cannot be edited safely.

**Keep our rules in a separate script and `include` it.** Stalwart supports `include`
(`maxIncludes: 3`), and this would leave foreign scripts untouched entirely. Rejected for now
because `include` is not in Stalwart's advertised `sieveExtensions` list, so a client cannot check
for it the way it checks everything else, and a deployment without it would fail at delivery time
rather than at save time. Worth revisiting if it becomes advertised.

**Structured rules as a server-side object** (what Fastmail actually does — its web client uses a
proprietary `Rule` type and does not speak RFC 9661 at all, and Apache James' TMail has its own
`Filter/set`). Not available to us: it requires a server extension, and Waxwing has no server.
